# Bloomery CLI Area

Bloomery exposes three application commands, plus help generated by its CLI
parser:

- [`bloomery check`](CHECK/README.md) runs static validation and Nix checks in
  parallel, with bounded summaries and seekable retained failure details.
- [`bloomery review`](REVIEW/README.md) renders a read-only catalog of manual
  requirements.
- [`bloomery sync`](SYNC/README.md) maintains Cargo and Bloomery locks, optionally
  updates Rust and Nix dependencies, and reports unconfigured recommendations.

The command syntax and options are specified by the
[CLI interface](INTERFACE/README.md). The reusable configuration, specification
loading, requirement-model, and scanning contracts live in the
[PARSER area](../PARSER/README.md).

## Boundaries

The CLI composes repository-local configuration and specification loading,
static evidence scanning, relational validation, bounded output, test/build
orchestration, and explicit lockfile maintenance. Sync changes locks and may
access the network. Check leaves source and locks unchanged, but executes Nix
builds and writes a user-cache run store. Review remains a read-only catalog.
Check does not own approvals, ticket management, or human review scheduling.
Generated Nix outputs no longer include `bloomery:check`; the runner invokes
other Nix checks directly. See [Nix orchestration](CHECK/design/workspace-check.md).

## System flow

```text
configuration and specifications ──► PARSER ──► requirement model ───────┐
                                                                          ├──► `bloomery check`
Rust / TypeScript / Nix evidence ────► PARSER/SCANNING ─► evidence registry┘
flake checks.<system>.* ────────────► Nix wrapper ─────────────► `bloomery check`
                                      requirement model ───────► `bloomery review`
Cargo manifests + raw config + optional flake ──► `bloomery sync` ──► locks + notices
```

## Model invariant

Every feature has at least one grouped requirement file. Requirement records are
validated according to the [requirements design](../PARSER/REQUIREMENTS/README.md),
associated with living architecture, and consumed by check and review. Sync
must not depend on loading or validating these records. The
filesystem and document contracts are specified by
[PARSER/WORKSPACE](../PARSER/WORKSPACE/README.md).
