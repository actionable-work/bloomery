# Bloomery CLI Area

Bloomery exposes seven application commands, plus help generated by its CLI
parser:

- [`bloomery init`](INIT/README.md) scaffolds a new Bloomery flake and Rust
  workspace from a bundled template. It is the only command that does not
  require a root `flake.nix` or `.bloomery/config.toml`.
- [`bloomery check`](CHECK/README.md) requires a root `flake.nix`; execution
  runs `nix fmt` before static validation and Nix checks, then runs independent
  checks in parallel with terminal work metrics, bounded summaries, and
  seekable failure details.
- [`bloomery disk`](DISK/README.md) reports the realized Nix store closure size
  of the Bloomery packages and checks tree, or one addressed derivation; its
  `tree` command renders the category breakdown.
- [`bloomery review`](REVIEW/README.md) renders a read-only catalog of manual
  requirements.
- [`bloomery sync`](SYNC/README.md) maintains Cargo and Bloomery locks, optionally
  updates Rust and Nix dependencies, and reports unconfigured recommendations.
- [`bloomery config`](CONFIG/README.md) reads and edits every
  `.bloomery/config.toml` key through schema-typed keys, materializes absent
  recommended keys, compares recommendations with the current configuration,
  and annotates configured keys with schema-catalog documentation.
- [`bloomery spec`](SPEC/README.md) creates, reads, updates, and removes
  requirement records, then projects the tests tied to a requirement and the
  untied tests that are graduation candidates.

The command syntax and options are specified by the
[CLI interface](INTERFACE/README.md). The reusable configuration, specification
loading, requirement-model, and scanning contracts live in the
[PARSER area](../PARSER/README.md).

## Boundaries

The CLI composes repository-local configuration and specification loading,
static evidence scanning, test-site discovery, relational validation, bounded
output, test/build orchestration, explicit lockfile maintenance, and schema-typed
configuration and requirement editing. Sync and config change locks and
configuration respectively; spec mutations change requirement records. Mutating
`config` commands create a missing configuration file with a warning. Every
application command, including check retrieval, disk, review, sync, and spec,
requires a root `flake.nix`. `init` is the bootstrap exception, `config` is
exempt but warns when the flake is absent, and parser help and version output is
served without a preflight. Check execution
runs the formatter before checks and may modify workspace source; lockfiles
remain unchanged. Config edits `.bloomery/config.toml` and leaves lockfiles and
source unchanged. Config documentation edits only the comment layer of the
configuration file. Spec editing changes only grouped requirement records and
leaves configuration, design documents, source, and lockfiles unchanged. Check
executes Nix builds and
writes a user-cache run store. Review remains a read-only catalog. Disk
measures realized store paths without building or mutating anything. Spec
trace and candidate discovery are read-only projections over the requirement
tree and discovered test sites. Check does not
own approvals, ticket management, or human review scheduling.
Generated Nix outputs no longer include `bloomery:check`; the runner invokes
other Nix checks directly. See [Nix orchestration](CHECK/design/workspace-check.md).

## System flow

```text
`bloomery` commands
├── `bloomery init`
│   └── bundled template catalog ──► target scaffolding + seeded specs ──► lockfiles
└── current directory + `flake.nix` presence gate
    ├── `bloomery check` execution
    │   ├── catalog/selection setup
    │   ├── flake formatter ──► `nix fmt`
    │   └── after formatting: PARSER/static checks + Nix checks
    ├── `bloomery disk` ──► realized Nix store closure measurement
    ├── `bloomery review` ──► requirement model
    ├── `bloomery spec` ──► requirement record edits + discovered test sites
    ├── `bloomery sync` ──► Cargo and Nix lock maintenance
    └── `bloomery config` ──► schema-typed config.toml edits and upgrade
```

## Model invariant

Every feature has at least one grouped requirement file. Requirement records are
validated according to the [requirements design](../PARSER/REQUIREMENTS/README.md),
associated with living architecture, and consumed by check, review, and spec.
Sync
must not depend on loading or validating these records. The
filesystem and document contracts are specified by
[PARSER/WORKSPACE](../PARSER/WORKSPACE/README.md).
